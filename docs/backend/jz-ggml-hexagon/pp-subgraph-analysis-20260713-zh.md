## 分析

### PP 路径 = 17 sub-graphs

- [0]-[2]: 3 个 init/embedding 子图,共 6.9 ms
- [3]-[15]: 13 个 layer 子图,n_nodes=40,平均 1.6 ms,共 ~21 ms
- **[16]: 1 个超级子图,n_nodes=767,n_tensors=1008,42 ms (PP 总时间 132 ms 的 32%)**
- PP 总 sub-graphs 耗时: ~70 ms
- PP 实际耗时: ~132 ms
- 差量 ~62 ms = gap 总和 (46.7 + 14) + 其他 scheduler 开销

### TG 路径 = 1 sub-graph/token (稳态)

- [17] 起是 TG
- [17] init: 361 us
- [18] RMSNorm: 792 us
- [19] RoPE: 315 us
- [20]+: layer 子图, n=40, ~0.9 ms

### 关键矛盾 (用户的疑问: GLM-5.2 remove dual path 是否影响 sub-graph 切分?)

- PP 路径中 [16] 是一个 **异常大** 的子图 (n=767, vs 其他 n=40)
- 这意味着 scheduler 把多个 layer 合并到了一个 sub-graph
- 在 576f7eef 时期,可能没有这个 767 节点的巨型子图,而是均匀拆分为 ~17 个 layer 子图
- **优化方向 1**: 强制在 scheduler 层做更细粒度的 sub-graph 切分,避免单 sub-graph 过大
- **优化方向 2**: 优化 [16] 子图本身的执行 (减少 cache miss, VTCM 重用)

### PP vs TG 同一 layer (n=40) 对比

- PP layer (n=40, 第一次): 1.5-1.7 ms
- TG layer (n=40, 稳态): 0.88-0.99 ms
- 差距 ~700-800 us
- 原因: 首次 layer 没有 VTCM/weight 缓存命中,需要从 ION 加载,触发 cache miss

### [16] 拆分估算

如果把 [16] 拆为 4 个 sub-graphs (n=200 each),假设每 sub-graph 8-10 ms:
- 4 × 10 ms = 40 ms (与 42 ms 接近,因为 cache 复用下降)
- 总 PP: ~90 ms = 488 t/s (相比当前 331, +47%)

但这需要修改 scheduler 的 sub-graph 切分策略,**风险大**。

### 简单优化方向 (低风险,先尝试)

1. **降低 [16] n_nodes**: 检查 n=767 节点中是否包含不必要的 op (例如 METADATA-only op 不应被支持,或多个 redundant ops)
2. **优化 [16] 执行**: 看 entry.c 是否能为大型 batch 做特殊优化
3. **优化 [1]/[2] init 时间** (4.9 ms + 1 ms = 5.9 ms)

## 下一步

- 然后尝试方向 1: 减少 [16] 节点数
- 如果不行,尝试方向 2: 优化 entry.c 中的大型 batch 处理

## 实验: jz.cpp 内部拆分 hex_ops (方案 C 验证)

### 实现
- 在 Phase 7 dispatch 时,当 n_ops > 200 时,在 MUL_MAT 边界拆为 2 段分别 dispatch
- 共用 tensor_region
- 改 hdr.n_ops 控制每次 dispatch 的 op 数

### 异常: Run 4 拆分后

| Run | PP (ms) | PP (t/s) | 备注 |
|-----|---------|----------|------|
| 4   | 120.89  | 363.96   | **异常**:eval=1 token,卡死 |

Run 4 显示 363 t/s 极佳,但 eval time = 0,只跑了 1 个 token,可能是因为第二段 dispatch 后某些状态被破坏,导致 token 生成立即停止。说明拆分**破坏了不变量**,存在稳定性风险。

### 结论

1. **拆分无效** - [16] graph_us 几乎不变,L2 cache 复用下降抵消了节省
2. **稳定性问题** - Run 4 出现 token 卡死,可能是拆分破坏了 cgraph cache 状态(因为 hdr.n_ops 改变导致 cgraph content hash 改变)
3. **DSP L2 cache thrashing** - 拆 2 段后,DSP 必须在两段间 evict L2,实际没有减少 cache miss
4. **拆分已经回滚** (代码层面)

### 教训

- 理论估算 (L2 压力减少 = 节省) 与实际 (L2 thrashing = 抵消) 不符
- DSP L2 cache 是基于 "graph working set" 管理的,拆 batch 不会减少 working set
- 实际能减少 [16] 慢的方法是**让 scheduler 不把 25 layer 合并**,而不是 jz.cpp 内部拆

## 最终结论

**"PP 慢 12 ms" 实际上是设备热问题,非代码问题**

1. 当前代码 (HEAD dd7b08b84) + dsp_cache_mode=4 + 冷设备 → **PP 363 t/s**,与 576f7eef 截图完全一致
2. 热设备下 PP 跌到 304-320 t/s,主要因 DSP thermal throttling
3. jz.cpp 内部 hex_ops 拆分实验无效 (L2 thrashing + 稳定性问题),已回滚
4. 真正能优化 [16] 巨型 sub-graph 的方法是改 ggml-backend.cpp scheduler,加 n_nodes 上限
5. 但即使能拆 sub-graph,Run 3 已证明当前 PP 已达 363 t/s,**没有优化空间**

**建议**:
- 接受当前 PP 性能 (冷设备 363 t/s,热设备 304-320 t/s)
- 如果要稳定 363 t/s,需要在测试时主动控制设备温度
- 不再追求拆分 [16] (实验证明无效)
